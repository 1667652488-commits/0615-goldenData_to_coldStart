符合如下类别的属于"失败/部分通过"，共 5 条有效规则：

①交易执行前缺乏用户确认环节：
	判定标准：Agent在交易执行前缺乏用户确认环节：在用户选择产品并指定金额后，agent未向用户展示完整的交易摘要（产品名称、金额）并获得用户明确确认，直接基于用户单次表达就跳转到资金筹划或购买执行步骤。具体表现为：当用户表达购买意向后，agent立即进行余额查询、资金调入、购买执行等操作，跳过了向用户展示交易明细并请求确认的关键步骤。
	检查条件：
		当 在agent执行购买或转账操作前（以系统日志或agent回复中的执行语句为准），agent的上一条回复中是否包含了完整的交易摘要（产品名称、金额、资金来源/目的）并询问用户“确认”或“是否同意”
		→ agent 必须：agent在展示摘要后，回复中有“确认”“是否同意”“请确认”等明确要求确认的语句
		→ 否则判定为「交易执行前缺乏用户确认环节」
		当 在用户提出修改已确定或已执行金额后，agent执行新的购买操作前，agent的最后一条回复是否包含新的交易摘要（产品名称、修改后的金额、资金来源/目的）并询问用户“确认”
		→ agent 必须：用户修改金额后，agent在回复中呈现了包含新金额的摘要，并附带“确认”“是否同意”等确认询问
		→ 否则判定为「交易执行前缺乏用户确认环节」
	典型表现：
		○ 负例：agent在用户表达购买意向后，没有展示交易摘要并请求用户确认，而是直接进入资金筹划和购买流程，违反了交易前需用户确认的规则。
		○ 负例：agent在用户表达购买意向后，仅提取了产品和金额，就直接透传至fund_planning_skill，未向用户展示交易摘要并请求确认，直接导致交易被无条件执行。
	责任归属：
		- 主要：product_select_skill_added_v5 — confirm分支直接透传至fund_planning，缺少用户确认环节（置信度 90%）
		- 次要：fund_planning_skill_added_v5 — 接收透传后直接执行购买，未要求用户再次确认（置信度 80%）
		- 次要：AgentRule_added_v5 — Human-in-the-loop中断规则未覆盖交易确认环节（置信度 60%）
	[排名 #1 | 综合0.78 = 合理性0.70 × 0.4 + 重要性0.95 × 0.3 + 频率0.71 × 0.3]

②用户输入格式或语义错误未校验确认：
	判定标准：Agent 在用户输入金额包含非法字符（如 emoji、数字符号）时，未进行格式校验或语义确认，直接照单全收并作为正常金额处理，导致系统接受了非法输入，用户也未得到纠正反馈。
	检查条件：
		当 当用户输入的金额字符串中包含非数字字符（如emoji、标点符号、字母）时，agent的下一轮回复中是否出现了“格式校验”“金额格式不正确”“请使用数字格式”或等效表述，并提示用户重新输入标准格式
		→ agent 必须：agent回复中包含上述任一校验语句或提示
		→ 否则判定为「用户输入格式或语义错误未校验确认」
		当 当用户输入的产品名称与数据库/系统内正式名称不完全匹配（如错别字、别名、模糊表述）时，agent的下一轮回复中是否包含了向用户确认产品名称的语句（如“您说的是不是XX？”“是否指XX产品？”）
		→ agent 必须：agent回复中包含向用户确认名称的语句
		→ 否则判定为「用户输入格式或语义错误未校验确认」
	典型表现：
		○ 负例：用户输入的金额包含 emoji 数字符号（1️⃣0️⃣0️⃣0️⃣0️⃣），agent 未进行任何格式校验或请求确认，直接当作正常金额透传并执行后续流程，违反了金额输入应进行校验和确认的规则。
	责任归属：
		- 主要：product_select_skill_added_v5 — 金额原文提取规则禁止格式校验和清洗，导致非法字符透传（置信度 95%）
		- 次要：AgentRule_added_v5 — 缺少对用户输入格式的通用校验与确认规则（置信度 60%）
	[排名 #2 | 综合0.65 = 合理性0.70 × 0.4 + 重要性0.77 × 0.3 + 频率0.45 × 0.3]

③转账金额精度未保留或未确认：
	判定标准：Agent 在展示转账或购买金额时，未将金额转换为精确到分位的标准数值格式（如'50000.00元'），而是直接使用用户输入的原始表述（如'5万块'、'1万8千'），也未在确认环节要求用户对精确金额进行确认，导致金额精度未保留或未确认。
	检查条件：
		当 在agent执行转账操作前（以系统日志或agent回复中的执行语句为准），agent的最后一条回复是否包含了精确到分位的转账金额（如“499,000.00元”而非“499,000元”）并附有“确认”语句
		→ agent 必须：agent展示的金额包含小数点后两位（如.00）且中或英文逗号分隔符合规范，并附有确认询问（如“请确认转账金额为499,000.00元”）
		→ 否则判定为「转账金额精度未保留或未确认」
	典型表现：
		○ Agent 在回复中展示金额为'5万元'和'1万8千元'，均为用户原文的近似表述，未转换为精确到分位的数值格式（如50000.00元、18000.00元），也未要求用户对精确金额进行确认，违反规则。
		○ Agent 展示的金额'20000元'和'5000元'均未显示分位（如20000.00元、5000.00元），但金额本身为整数，未强制要求用户对精确到分位的金额进行确认，违反规则。
	责任归属：
		- 主要：product_select_skill_added_v5 — confirm分支中amount直接透传用户原文，未做精度转换（置信度 90%）
		- 次要：fund_planning_skill_added_v5 — 资金筹划时未强制要求金额转为分位格式并确认（置信度 70%）
		- 次要：AgentRule_added_v5 — 缺少全局规则要求展示精确金额并经用户确认（置信度 60%）
	[排名 #3 | 综合0.58 = 合理性0.55 × 0.4 + 重要性0.60 × 0.3 + 频率0.60 × 0.3]

④后台异常时的透明兜底缺失：
	判定标准：当后端MCP工具超时或返回重复数据时，agent未向用户透明解释故障，而是将重复推荐假装为新推荐展示，导致用户混淆与不满。
	检查条件：
		当 在最后一轮agent回复中，当数据库或系统日志显示后台出现超时/降级/重复数据时，agent回复中是否出现了“系统暂时无法”、“无法提供新推荐”、“数据与上次相同”或等效表述（如“MCP超时”“降级”）
		→ agent 必须：agent回复中包含上述任一表述（或明显同义表述）
		→ 否则判定为「后台异常时的透明兜底缺失」
	典型表现：
		○ MCP超时后，agent未向用户说明数据异常，直接展示重复的推荐列表，假装为新推荐，导致用户不满，违反透明兜底规则。
	责任归属：
		- 主要：AgentRule_added_v5 — 缺少MCP异常时的透明化处理和兜底规则（置信度 90%）

⑤用户身份或操作对象未明确时未核实：
	判定标准：用户未明确指定具体银行卡号时，Agent 没有先要求用户确认或指定卡号，而是直接基于默认账户或假设执行查询操作，导致用户质疑其操作准确性。
	检查条件：
		当 在用户未提供具体卡号/账户标识（例如仅说“查余额”“查我账户”）时，agent的下一轮回复中是否包含了询问卡号/账户或要求用户确认账户的语句（如“请问您的卡号？”“您卡尾号是XX吗？”“您查询的是哪个账户？”）
		→ agent 必须：agent回复中包含上述询问或确认语句
		→ 否则判定为「用户身份或操作对象未明确时未核实」
	典型表现：
		○ 负例：用户在对话开始时未明确指定具体银行卡号，Agent 未要求用户核实身份或指定卡号，直接执行查询操作，导致用户提出质疑。虽然 Agent 后续承认疏忽并询问卡号，但首次操作已违反规则。
	责任归属：
		- 主要：AgentRule_added_v5 — 缺少对'用户身份或操作对象未明确时需先核实'的约束（置信度 90%）
