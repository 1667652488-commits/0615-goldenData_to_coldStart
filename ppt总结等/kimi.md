## PPT 整体设计理念

- **主题**：从 Badcase 到可部署规则的端到端流水线
- **主线**：联调方案（黄金数据标注 → 桥接筛选 → 冷数据规则提取 Phase2-6）
- **副线**：方法论沉淀（系统理解 6 点、最终状态原则、经验元体系）
- **风格**：延续 v3 浅色商务风，主色深绿 `#4CAF50`，辅色蓝 `#2E75B6`、橙 `#E67E22`、紫 `#8E44AD`
- **页数**：22 页

## 第 4 页：LLM Agent 评估的冷启动困境

- **标题**：LLM Agent 评估的冷启动困境
- **左栏：行业背景（3 点）**
  - LLM Agent 在金融、客服等高合规领域加速落地
  - 现有基准测能力上限，不关注合规缺陷
  - 工业界卡在"评估什么"——规则从哪来
- **右栏：实际痛点（4 点）**
  1. 规则空白：新业务无现成规则，人工编写 2-4 周
  2. 标注成本高：逐条标注错误类别，专家瓶颈
  3. 工具割裂：黄金数据标注 与 冷数据规则提取 各自为战
  4. 规则不可操作：自然语言描述 ≠ 评估器可执行条件
- **底部强调条**：30-100 条轨迹 + 2 小时 → 替代 2 周人工归纳

## 第 5 页：两个工具的割裂与联调必要性

- **标题**：从"两张皮"到"一条线"
- **上方表格**：对比两个工具
  | 工具 | 输入 | 输出 | 局限 |
  |---|---|---|---|
  | 黄金数据标注 | 无标注轨迹 | golden_output.jsonl（result + reason）| 只评判，不产规则 |
  | 冷数据规则提取 | 失败轨迹 | rules.json + 自然语言规则 | 依赖人工预筛选 |
- **下方流程图**：
  - 标注工具输出 → 桥接筛选（过滤失败/部分通过） → 冷数据工具输入
  - 标注：直觉式 few-shot 评判；规则挖掘：LLM 归纳 IF-THEN 规则
- **关键结论**：联调后形成"无标注轨迹 → 可部署规则"完整流水线

## 第 7 页：全局架构图

- **标题**：黄金数据标注 × 冷数据规则提取 联调架构
- **核心图**：横向 7 个步骤的流程图
  1. **Phase1 黄金数据标注**：无标注轨迹 → 全局理解 → 直觉评判 → golden_output.jsonl
  2. **桥接筛选**：过滤 result ∈ {失败, 部分通过} → badcase_traces/
  3. **Phase2 链路归纳**：归纳正确链路 + 缺失检查点
  4. **Phase3 类别归纳**：归纳 badcase 类别 + 二进制检查点
  5. **Phase4 特征提取**：LLM 逐条判定 0/1/NA
  6. **Phase5 规则挖掘**：IF-THEN + Skill 归因 + Few-Shot
  7. **Phase6 规则转换**：自然语言化 + 三维排序筛选
- **关键数据标注**：
  - 标注成本：仅需通过/失败
  - 冷数据输入假设：全部是 badcase
  - 输出：rules.json / rules_natural_language.txt / rules_ranked.json

## 第 8 页：Phase1 黄金数据标注

- **标题**：Phase1：直觉式黄金数据标注
- **左栏：两阶段流程**
  - 阶段一：全局场景理解（生成 global_understanding.txt）
  - 阶段二：逐条直觉评判（expected_behavior + result + reason）
- **右栏：关键设计**
  - 仅标注 result ∈ {通过, 失败, 部分通过}
  - 无需分析具体错误类别
  - 输出保留原始 history 字段，供下游读取
- **底部提示**：关键改动 —— 输出追加 conversation_id / script_id / history / max_turns / total_turns

## 第 9 页：Phase2 链路归纳

- **标题**：Phase2：从 Badcase 反推正确链路
- **左栏：批次迭代归纳**
  - Batch1（10 条）：从零归纳标准链路 + 初始检查点
  - Batch2+：审阅优化，合并/新增检查点
  - 默认不去重：重复轨迹代表场景高频出现
- **右栏：输出示例**
  - 标准链路：8 个步骤（身份核验 → 推荐 → 选品确认 → 交易确认 → 资金筹划 → 修改订单 → 信息查询 → 异常处理）
  - 缺失检查点：9-15 个，每个含触发条件 + 判定标准 + 违反动作
- **关键原则**：检查点必须是"强制约束"，不是"注意事项"

---

## 第 10 页：Phase3 类别归纳

- **标题**：Phase3：从检查点归纳可判定类别
- **左栏：两阶段归纳**
  - Step1：LLM 自由聚类，不预设类别框架
  - Step2：审查校验三要素（可判定性 / 客观性 / 证据位置明确）
- **右栏：参数控制**
  - --min-categories / --max-categories：按轨迹数量动态约束
  - 核心原则：类别数 ≈ 检查点数 / 2~3
- **底部案例**：15 个检查点 → 5 个类别 / 11 个二进制检查点 / 100% 轨迹覆盖

---

## 第 11 页：Phase4 特征提取

- **标题**：Phase4：LLM 理解式特征提取
- **核心图**：特征矩阵（轨迹 × 检查点）
  - 0 = 违反，1 = 通过，NA = 不适用
- **关键设计（4 点）**：
  1. 三值判定：NA 排除不相关轨迹
  2. 批量判定：一次 LLM 调用判多个检查点
  3. 缓存机制：相同 checkpoint+轨迹不重复调用
  4. 轨迹格式配置化：不绑定特定数据格式
- **数据示例**：19 条轨迹 × 8 个检查点 = 152 个判定

---

## 第 12 页：Phase5 规则挖掘

- **标题**：Phase5：规则挖掘 + Skill 归因
- **左栏：流程**
  1. 按类别聚合特征矩阵
  2. 筛选 top-K 检查点 + 典型轨迹
  3. LLM 归纳 error_reason + if_conditions + skill_attribution + few_shots
  4. 后处理：skill 白名单校验 + 重试 3 次 + 降级兜底
- **右栏：规则 JSON 示例**
  - id / error_category / if_conditions / skill_attribution / few_shots / confidence
- **关键价值**：规则可直接被评估器执行，Skill 归因精确到文件名

---

## 第 13 页：Phase6 规则转换与排序

- **标题**：Phase6：规则语言化 + 三维排序筛选
- **左栏：规则语言化**
  - 将 rules.json 转为自然语言规则文本
  - 采用"当…时，必须…，否则判定为…"三元组
  - 供 checker / 评估器作为提示词输入
- **右栏：三维排序**
  - 合理性（LLM 对抗性审查）
  - 重要性（severity + 业务影响）
  - 出现频率（支撑轨迹数 / fail 率）
  - score = 0.4×合理性 + 0.3×重要性 + 0.3×频率
- **输出**：rules_natural_language.txt + rules_ranked.json

## 第 15 页：提示词优化 — 系统理解与最终状态

- **标题**：提示词优化两大方法论
- **左栏：系统理解 6 点（针对 Phase2）**
  1. 系统概况：agent 角色与能力边界
  2. 常见场景：典型用户场景
  3. 用户目标：用户通常想达成什么
  4. 常见转折：关键节点与转折
  5. 常见陷阱：agent 易出错环节
  6. 系统缺陷模式：技术限制 vs 逻辑缺陷
- **右栏：聚焦最终状态原则（针对 Phase3）**
  - 描述"最终应达成的正确状态"，而非"具体步骤"
  - 用"确保…""在…前提下完成…"等概括性表述
  - 聚焦安全、合规、用户体验
- **底部案例**：
  - ❌ "agent 是否清洗金额为纯数字"
  - ✅ "确保用户在清晰获知标准化金额的前提下予以确认"

## 第 16 页：经验元体系

- **定义**：经验元 = 智能体执行任务过程中产生的最小可复用经验单元
- **三类经验元卡片**：

- **底部闭环**：标注数据 → 规则元 → 评估器 → 反思元 → 归纳 → 新规则元 → 案例元更新
