# Phase2/3 提示词优化讨论：根因分析与最终状态原则

> 日期：2026-06-12
> 状态：已对齐思路，待执行

## 一、问题发现

基于 `历史结果\0611_pipeline_newtask_good\rules.json` 中的运行结果，发现两个提示词层面的问题：

### 问题 1：R001 "重复推荐未去重"——根因误判

**现象**：规则 R001 归纳为"agent 换一批时未做去重校验，导致返回重复产品"。

**实际轨迹**（auto-efc489，script_id = AUTO_工具调用超时重试_01）：
```
Agent: MCP 超时了，按流程继续调用低码平台获取补充信息。
Agent: 根据您的条件没有找到合适产品...目前系统返回的产品列表和之前是一样的
```

**真正根因**：MCP 工具调用超时/失败，降级后返回相同结果。Agent 的缺陷不是"没有做去重校验"，而是"工具调用失败后没有用兜底话术告知客户当前无法换一批"。

**错误链条**：
- Phase2 归纳检查点时，LLM 只看"结果重复"的表象 → 归纳为 CP002 "换一批需去重比对"
- Phase3/4/5 沿着错误继续 → 最终规则 R001 整体跑偏

**本质缺陷**：Phase2 提示词缺少引导 LLM 区分"现象"和"根因"的机制，尤其对"技术限制导致的异常"缺乏认知。

### 问题 2：R003 "非标准输入未清洗校验"——判定标准不完整

**当前 judgment_criteria**：
```
True：agent在下一轮回复中展示的金额为纯阿拉伯数字（如'10000元'），
      且明确表示'将按10000元购买'或类似含义。
```

**缺陷**：
- 只要求"清洗并回显"，缺少"告知客户不要输入 emoji 等非标准格式"的引导
- 正确行为应该是：清洗转换 → 回显确认 → **提醒用户后续请使用标准格式**
- 当前判定标准只覆盖了"处理"这一步，没有覆盖"引导"这一步

**本质缺陷**：Phase3 提示词在定义 judgment_criteria 时，倾向于描述"中间步骤"（做 X 步骤），而非"最终应达成的状态"（确保 X 条件被满足）。

## 二、优化方案

### 2.1 R001 相关：系统理解指引

**用户提出的 6 点方法论**（概括性强，适用于任何系统）：

| 维度 | 引导 LLM 思考什么 | 解决什么问题 |
|---|---|---|
| 系统概况 | agent 的角色和能力边界是什么？ | 建立 LLM 的系统上下文认知 |
| 常见场景 | 轨迹中出现了哪些典型的用户场景？ | 使检查点归类贴合实际场景 |
| 用户目标 | 用户通常想要达成什么？ | 从用户视角判断何为"错误" |
| 常见转折 | 对话中经常出现哪些关键节点或转折？ | 聚焦关键决策点 |
| 常见陷阱 | agent 最容易在哪些环节出错？ | 定位高风险环节 |
| 系统缺陷模式 | agent 的异常行为是否可能由技术限制导致？ | 区分"逻辑缺陷"和"技术限制"，避免误归因 |

**与"区分现象和根因"的补丁式写法对比**：
- 补丁式：只覆盖具体已知场景（如"如果看到 MCP 超时怎么办"）
- 方法论式：LLM 自行识别任何系统的技术缺陷模式，不需要枚举

### 放置位置

**Phase2 `INITIAL_SYSTEM_PROMPT`**——分析步骤的前置环节：

```
系统理解（内化思考，不需在输出中逐条回答）：
在开始标记错误之前，先从以下维度理解这个系统：
- 系统概况：agent 的角色和能力边界是什么？
- 常见场景：轨迹中出现了哪些典型的用户场景？
- 用户目标：用户通常想要达成什么？
- 常见转折：对话中经常出现哪些关键节点或转折？
- 常见陷阱：agent 最容易在哪些环节出错？
- 系统缺陷模式：agent 的异常行为是否可能由技术限制导致？
  （如工具调用失败、接口超时、MCP 不通、知识库缺失、
   依赖的外部系统不可用等。若是技术限制导致，
   归纳的检查点应针对"技术限制下的兜底处理"而非"逻辑缺失"）
```

**Phase2 `REFINE_SYSTEM_PROMPT`**——审阅时也要带着系统认知：

呼应系统缺陷模式，审阅已有检查点是否误将技术缺陷归为逻辑缺陷。

**关键设计决策**：这 6 点是"内化思考指引"，不要求 LLM 在输出中逐条回答。原因：
- 轨迹已经很长，LLM 注意力和输出长度有限
- 占用输出 token 会压缩真正用于归纳检查点的部分
- LLM 在内化思考后自然会影响后续分析质量

### 2.2 R003 相关：聚焦最终状态原则

**用户提炼的原则**（适用任何检查点，不限于输入校验）：

```
聚焦"最终状态"原则（重要）：
- 描述的是「最终应该达成的正确状态」，而非「具体步骤」
- 从原则层面概括，不要陷入中间细节
- 说明最后一轮应该达成什么目标
- 聚焦到安全、合规、用户体验等核心目标上
- 用"在...前提下完成...""确保...""尊重..."等概括性表述
```

**与"检测→清洗→确认→引导"流水线式写法对比**：
- 流水线式：仅适用于特定场景（输入校验），换场景要重新枚举
- 最终状态式：通用原则，任何检查点的判定标准都适用

**示例对比**：

| 写法 | judgment_criteria |
|---|---|
| 步骤式（当前） | agent是否在下一轮回复中将金额清洗为纯数字格式并回显 |
| 最终状态式（优化后） | 确保用户在清晰获知标准化金额的前提下予以确认，且被引导后续按标准格式操作 |

### 放置位置

**主位置：Phase3 `PHASE3_SYSTEM_PROMPT`**——judgment_criteria 编写规范：

```
检查点判定标准编写原则：
- 聚焦"最终状态"而非"具体步骤"：
  描述「最终应该达成的正确状态」，而非「中间应该执行什么动作」
- 从原则层面概括，不陷入中间细节：
  不是"agent 应该做 X 步骤"，而是"确保最终 X 条件被满足"
- 说明最后一轮应该达成什么目标
- 聚焦安全、合规、用户体验等核心目标
- 用"在...前提下完成...""确保...""尊重..."等概括性表述
```

**辅助位置：Phase2 `INITIAL_SYSTEM_PROMPT`**——enforcement 写法标准加一句：

```
- enforcement 描述的是"违反此约束后应达到的最终纠正状态"，而非"执行某个具体步骤"
```
